# code-invariants

**Executable code invariants and complex best-practice enforcement beyond traditional linting.**

AST-based rules, semantic DRY checks, mandatory test presence, and architectural fitness functions — primarily for TypeScript and Python. Designed for AI coding agents and CI gates that can largely replace human review of *structural* quality.

> If the code passes the invariants, a human reviewer can focus almost exclusively on business logic and product correctness.

## The Problem

AI coding agents are extremely productive, but they are not reliable at consistently honoring high-level instructions in large contexts or large repositories.

- Instruction files (Cursor rules, CLAUDE.md, AGENTS.md, etc.) are a good starting point but are **not enforced**.
- Linting and formatting catch only superficial issues.
- Type systems help a lot but still miss many structural and compositional patterns.
- A human cannot properly review a 2–5k LOC PR generated by an agent.

Concrete examples that instructions try to solve but cannot reliably enforce, and that classic linters fall short of:

1. Every data query (e.g. TanStack `useQuery`) must have proper error handling (`onError` or equivalent exhaustive handling).
2. Only semantic styling tokens are allowed — a design system exists, but nothing stops the model from inventing non-semantic CSS classes or raw values.
3. Every page/component that performs data fetching must properly handle and render the three states: **loading**, **error**, and **success** (e.g. via a compositional `DataRegion` pattern).

These are solvable with wrapper components + custom TypeScript AST walkers (and equivalent tools in other languages). The key insight is **enforcement**, not just documentation.

Additional higher-order goals:

- **Semantic DRY**: After every PR, embed the repository into a vector store. Before an agent writes a new component/function, it must query for semantically similar existing code and reuse it when appropriate.
- **Mandatory test presence**: Every exported function/component must be referenced at least once in a test file (static check + coverage thresholds).
- Extensible to Python (and eventually other languages) with the same philosophy.

## Vision

Create a practical, multi-language toolkit that turns high-level engineering standards into **executable, CI-enforceable invariants**. The system should be:

- Fast enough for local + CI use
- Agent-friendly (MCP servers, clear error messages that agents can act on)
- Composable (rules as plugins / declarative configs)
- Focused first on TypeScript/React and Python

See [docs/VISION.md](docs/VISION.md) for the full vision and [docs/SPECS.md](docs/SPECS.md) for detailed specifications.

## Research Findings (Summary)

Extensive research (August 2026) showed:

- **No single product** currently delivers the full combination of complex compositional AST rules + proactive semantic vector DRY + static “every function appears in tests” gates + multi-language agent-oriented packaging.
- Strong building blocks exist:
  - **Semgrep** — excellent custom pattern rules across languages (static).
  - **ts-morph** + custom ESLint plugins — ideal foundation for TypeScript/JSX compositional rules (exactly what the original TSX prototype used).
  - **ArchUnitTS / ArchUnitPython**, dependency-cruiser, import-linter, Tach, Fensu — architecture fitness functions and layer rules.
  - **dupehound** — fast structural (fingerprint) clone detection with CI gate and MCP, multi-language, zero AI required.
  - **Slopo** — embedding-based semantic duplication detection.
  - Coverage tools (Vitest, pytest-cov, etc.) for function coverage.
  - sensez and similar agent-oriented structural feedback tools.

Almost all of the above are pure static analysis (or local embeddings). None require generative LLM API keys for the core checks.

Full research notes and comparisons are in [docs/RESEARCH.md](docs/RESEARCH.md).

## Status

Implementation has started. The repository is a pnpm/TypeScript workspace with the published plugin contract (`packages/code-invariants/src/index.ts`) and a CLI skeleton; **no rules are implemented yet** — `code-invariants check` currently reports that nothing is configured.

**Core architectural decisions are locked** in [docs/SPECS.md](docs/SPECS.md) (CLI shape, `defineConfig`, plugin contract, TypeScript-first core, no wrapping of Biome/ESLint, native AST per frontend, performance approach, etc.). An agent can treat those decisions as stable and start implementing against them.

The original author has a working internal TypeScript/TSX prototype for several of the compositional rules. The goal of this public repo is to generalise it, add the missing pieces (semantic DRY, Python, agent integration, test-presence gates), and make it a proper open-source project that coding agents can build upon.

## Development

Requires Node >= 22 (CI runs 24, the active LTS). pnpm 11 is pinned via `packageManager`, so
pnpm fetches the right version itself — no manual install needed.

```bash
pnpm install
pnpm build   # tsc -b across the workspace
pnpm test    # vitest
pnpm check   # biome (lint + format)
```

Layout: one package (`packages/code-invariants`) holding the core, the CLI, and the public
plugin types. It splits into separate packages when a second consumer appears — most likely
with the Python frontend.

## Roadmap (High Level)

1. **Phase 0** — Documentation & design ✅
2. **Phase 1** — Core TypeScript engine (ts-morph based) + first set of compositional rules (useQuery error handling, DataRegion-style state exhaustiveness, semantic style tokens)
3. **Phase 2** — CI integration, CLI, and basic MCP server so agents can query/check
4. **Phase 3** — Semantic DRY layer (vector index + similarity gate)
5. **Phase 4** — Python support (libCST / tree-sitter + equivalent rules)
6. **Phase 5** — Test-presence static checks + richer architecture fitness rules
7. **Phase 6** — Polish, documentation, example monorepos, community rules registry

## Contributing / Next Steps for Coding Agents

This repository is intentionally structured so that a coding agent can pick it up and start implementing.

Recommended first tasks for an agent:

1. Read `docs/VISION.md`, `docs/SPECS.md`, and `docs/RESEARCH.md` thoroughly.
2. Treat the **Locked decisions** section in `docs/SPECS.md` as binding.
3. Scaffold a TypeScript package with the core engine based on `ts-morph`.
4. Implement the first three example rules as plugins that obey the published contract.
5. Add a simple CLI (`npx code-invariants check`) with `--diff` / `--plugin` / `--rule` support and a GitHub Action.
6. Add tests for the rules themselves.

See `docs/SPECS.md` for precise interfaces and expected behaviour.
